# Teleclaude

Telegram bot bridging Claude Code to Telegram forum topics via Channels API + Agent SDK.

Each topic maps to a project directory with its own persistent Claude Code session (PTY + MCP channel server). macOS and Linux supported.

## Quick Reference

```bash
# Development
npx tsx src/index.ts start    # run in foreground
npm test                      # run tests (vitest)
tail -f ~/.teleclaude/logs/teleclaude.log   # view logs

# Service management
npx tsx src/index.ts install    # install as system service
npx tsx src/index.ts uninstall  # remove service
npx tsx src/index.ts status     # check service
npx tsx src/index.ts restart    # restart the service in place
npx tsx src/index.ts update     # git pull --ff-only + npm install + restart (git checkouts only)
npx tsx src/index.ts version    # print version (pkg version + git SHA)
npx tsx src/index.ts doctor     # environment preflight checks (read-only, safe while the daemon is live)

# Releasing (runs tests, tags, pushes)
npm version patch   # or: minor / major  →  host runs `update` to pull+restart

# One-shot install (deps + setup + service)
./scripts/install.sh

# Kill rogue processes
pkill -9 -f "tsx src/index"
pkill -9 -f "claude"
```

> Run `update`/`restart` from a terminal, **not** from inside a Teleclaude chat —
> restarting the daemon kills the channel server hosting that chat.

## Key Constraints

- **PTY required**: Claude Code needs a TTY for interactive mode (channels). `node-pty` provides this. Requires `chmod +x` postinstall fix for darwin prebuilds.
- **MCP launch command is mode-dependent** (`build-mode.ts`): a dev checkout launches the channel server as `npx tsx src/channel-server.ts` — NOT `node --import tsx`, whose loader breaks MCP stdio transport. A bundled build (dist/channel-server.js next to the running file) launches it as plain `node dist/channel-server.js` — verified by a 2026-08-21 spike: plain node over MCP stdio works; it was only ever the tsx loader that broke it.
- **Startup dialogs are answered on detection, not on a timer**: a new directory shows a workspace-trust dialog before the dev-channels warning, and nobody is at the keyboard. The old fix was blind Enters at 2s and 4s — a bet on render timing, and a third dialog would never be answered. `awaitsPromptConfirmation` (`channel-detect.ts`) matches the affordance every dialog prints (`Enter to confirm · Esc to cancel`, whitespace-insensitively, since the TUI eats spaces) plus the trust wording, and the PTY handler sends Enter when it appears — rate-limited (700ms) and capped (4), with its own buffer cleared per confirmation so the *next* dialog needs fresh output. The timed Enters remain as a fallback for a version that stops printing the affordance, now conditional on how many dialogs detection already handled. Extra Enters are harmless: an Enter at an idle REPL is a no-op, which is already the common case for a trusted project with only one dialog.
- **Single Grammy instance**: One bot token = one polling loop. Channel servers receive messages via HTTP.
- **Multi-user, multi-group**: `ownerTelegramIds` whitelists everyone allowed to use the bot (auth middleware in `daemon.ts`). Projects/sessions/processes are keyed by the composite `(chatId, topicId)` via the single `topicKey()` helper in `bot.ts` — Telegram topic IDs are only unique within a chat, so two groups can share a topic id. General-topic commands (`/new`, `/list`, `/delete`, `/status`) are scoped to the current group. This lets each person run their own group(s) plus shared groups; group membership is the access boundary. DM routing, DM scheduling and the continue picker additionally verify group membership via getChatMember before touching a project outside the current chat (`src/membership.ts`, 5-min cache) — the allowlist alone does not grant cross-group access. Old topic-id-only state is migrated on startup (`migrate.ts`).
- **Completed migrations are observability-gated; deletion deferred to a follow-up release**: boot converts the legacy `bypass` boolean to `permissionMode` (`migrateBypassBoolean`) and logs one `[migrate]` legacy-state count (`countLegacyState`: legacy session keys, `bypass` fields, chatId-less projects). The read fallbacks — `migrateToCompositeKeys`, `resolvePermissionMode`'s bypass branch + `SessionEntry.bypass`, and config.ts's chatId-less project fallbacks (`projectInChat`, `getProject`'s legacy `.find`, `backfillProjectChat`) — stay until a release whose boots report zero, and only the release *after* that deletes them (an install that skipped versions may still carry legacy state). `sweepProjectHooks` is NOT a retirement candidate: it cleans stale hooks out of users' project repos, not teleclaude's own state files.
- **Session continuity**: Session ids are persisted as soon as known (daemon callback), so conversations survive a restart/deploy and resume with context on the next message. Boot auto-spawn is gated on `lastActiveAt` (48h window, bumped on user messages and turn completion) to bound boot load while keeping cron-driven sessions alive. Legacy chatId-less projects self-heal on first message (`backfillProjectChat`). Queued boot auto-spawns re-check project + session state when their stagger timer fires (`autoSpawnDecision` in `session-state.ts` — a `/new`, `/delete` or `/model` in the window must win over what boot saw) and wrap `pm.spawn` in try/catch: a synchronous `pty.spawn` throw (renamed project dir, broken claude binary) used to hit the fatal `uncaughtException` handler and crash-loop under KeepAlive, taking every other topic down with it. `/stop` is deliberately NOT in that list: it never clears `sessionId`/`lastActiveAt` (only `/new` does — see below), so a queued auto-spawn can still resume a topic stopped during the stagger window. That's the same "next message resumes via the persisted session id" contract every other `/stop` call site relies on, not a bug.
- **Expired sessions self-heal**: Claude Code's retention sweep (`cleanupPeriodDays`, 30d) deletes transcripts while the session id lives on in `sessions.json` — and `--resume <swept id>` is fatal (`No conversation found with session ID`, exit code=1 in ~2s), so the topic died on *every* message, including hand-resent ones. `pm.spawn` now validates the id against the transcript on disk (`sessionTranscriptExists`) at the single spawn choke point and falls back to a fresh session; `sendToChannel` checks first so it can drop the id from `sessions.json`, tell the user the history is gone, and still deliver the message that triggered the spawn. `waitForReady` distinguishes `"died"` (this process exited — ours to retry) from `"gone"` (a newer generation owns the topic — hands off); conflating them was what turned a startup crash into a dropped message. A startup death with a resume id retries once without it; a death on an already-running process re-runs delivery once (`opts.respawned`), and the "Session disconnected" notice is suppressed while a delivery is still in flight.
- **Worktree/subfolder sessions are discovered dynamically, not assumed to live at the project root** (`sessionHomes`/`resolveSessionHome` in `sessions.ts`): Claude Code names a transcript's storage directory after the session's *cwd*, not "the project" — a session started in `.claude/worktrees/foo` lands in a sibling `~/.claude/projects/` directory from the root's, invisible to `/sessions`/`/resume` unless specifically looked for. Detection is two-step: a cheap `readdirSync` prefix filter over `~/.claude/projects` (`<rootDirName>-*`), then an exact check that reads the first `cwd` field out of a candidate's transcript and verifies real containment inside the project root (`isPathInside`, `path-containment.ts`) — the prefix filter alone false-positives on an unrelated sibling project whose name happens to start the same way (`teleclaude` vs `teleclaude-docs`, verified live). The homes list is cached per project root for 60s (project dirs appear rarely); a session's *own* current home is never cached — Claude Code physically **relocates** a transcript's directory when a session runs `ExitWorktree` (observed live: the worktree-named directory's `.jsonl` vanished and reappeared under the root's, with a `{"type":"relocated"}` record appended), so "where does this session live" can change mid-lifetime. Resuming a non-root-homed session persists its cwd as `SessionEntry.sessionCwd` (flows through `spawnSettingsFor` into `SpawnSettings.cwd`, which both the pty's `cwd` and `TELECLAUDE_PROJECT_PATH` use — `pm.spawn`'s own expired-transcript self-heal check, `resolveSpawnCwd`, validates against that resolved cwd too) so `/model` switches and boot auto-spawn keep resuming at the right place; `/new` clears it (a fresh session always starts at the root), and resuming a session whose home turns out to BE the root also clears it. **Accepted staleness window**: only an explicit `/resume` (`resumeSession` + `resumeCwdDecision` in `resume-cwd.ts`) re-resolves a session's home dynamically and refuses when a worktree was deleted; every *automatic* respawn (a plain incoming message, `/model`, boot auto-spawn) trusts the persisted `sessionCwd` as-is — a relocation that happens between an explicit resume and the next automatic respawn (requires a concurrent terminal session to run `ExitWorktree`) is a known, rare, low-cost gap: worst case is one more "session expired, starting fresh" cycle, never data loss. The two-writer `/resume` guard (`findLiveSession`/`resumeGuardDecision` in `live-sessions.ts`, below) has the same scope: it only runs on an explicit `/resume`, so every automatic respawn — a plain message, `/model`, boot auto-spawn, a scheduled run, or a webhook delivery — resumes the persisted session id unguarded. Accepted for the same reason: catching every path would mean re-checking the live-session registry on every message, and `/handoff`'s explicit two-writer warning text is the practical mitigation for the one workflow (terminal + Telegram on the same session) where this could actually collide. `/usage`'s per-session lookup resolves the current session's actual home the same way; broader usage aggregation (`getWeeklyUsage`, `/receipts`' token delta) staying root-only remains a deferred gap.
- **Transcripts are read in bounded chunks** (`forEachLine`/`forEachJsonLine` in `sessions.ts`): `/usage` aggregates every in-window transcript, and doing that with `readFileSync` + `split("\n")` cost a measured **142MB heap spike** (681MB on disk, 246MB in-window) — plus a 50MB-per-file skip that silently dropped big sessions out of the totals. Same numbers now for **4MB**, and the skip is raised to 512MB and re-framed as an event-loop-time guard rather than a memory one. Decoding goes through `StringDecoder` because a chunk boundary can land mid-character and transcripts are full of non-ASCII (`Crème`, `Café`, emoji) — naive per-chunk `toString()` corrupts them. Use `forEachLine` when a substring test can reject most lines before paying for a `JSON.parse` (as `readSessionRename` does, once per session in `/sessions`).
- **The callback server authenticates before reading the body**: everything the guard needs is in the query string, so an unauthenticated POST never gets to stream a body. Requests without a usable `(chat, topic)` pair used to skip the token check entirely and fall through to the "unhandled" log line — harmless in effect, but it let any local process write to the daemon log. Bodies are capped (`MAX_CALLBACK_BODY_BYTES`); rejections answer and then `req.resume()` so a refused caller doesn't leave a socket hanging.
- **Logging**: File-based (`~/.teleclaude/logs/teleclaude.log`). Never use `console.log` in daemon code.
- **Channel server replies directly**: Sends to Telegram via Bot API. Accumulates text and edits in place.
- **Tools are declared with `McpServer.registerTool` + zod** (`tool-schemas.ts`), not hand-written JSON Schema. The old schemas had drifted from the TS types: `android`/`ios` declared every field optional with only `action` required, while their action types are discriminated unions — so `{action:"install"}` passed validation and failed inside adb, and the call handler cast unvalidated input (`args.actions as AndroidAction[]`). Each schema now mirrors its module's exported type, `tool-schemas.test.ts` asserts assignability at compile time, and the requirements are documented to Claude instead of discovered by failing. `browse` stays deliberately loose (one shape, optional fields) because it soft-fails per action and finishes the sequence; tightening it would turn one bad step into a rejected batch. Errors still go through `runTool()`, which turns a throw into an `isError` result naming the tool — an exception out of a handler would kill the MCP server and take the topic with it.
- **Stop hook for done detection**: HTTP hook fires when Claude finishes a turn. Way more reliable than PTY parsing.
- **StopFailure auto-recovery**: A failed turn (`StopFailure` → `event=error`) leaves the Claude process alive but wedged — it stops pulling new channel messages, so further messages are silently dropped until `/new`. On the error event the daemon persists the live session id, then — for a NON-cancelled failure only — snapshots `rt.takeResendable()` **before** killing the process, and only then kills it: `kill()` synchronously fires the `killed` event, whose `dispose()` clears the runtime's `pendingTurn` queue (see below), so taking the snapshot after the kill would find it already empty. The snapshot is then **auto-resent in order**, each envelope at most once (marked resent before delivery, so a repeat failure can't loop) and reusing its original delivery id. User sees "♻️ Session reset — resending your last message(s)." A cancellation pending on the process (`hasCancelPending`) skips the snapshot entirely — never take, never resend, only the neutral cancellation notice — so a StopFailure that lands right after a Cancel-turn kill can never resend the message the user just asked to stop.
- **Delivery is idempotent and ledgered** (`DeliveryEnvelope` in `src/topic-runtime.ts` + `src/delivery-dedupe.ts`): every chat delivery carries `meta.delivery_id`, stable across retries of the same logical message, and the channel server drops an id it has already injected (bounded LRU, remembered only AFTER the MCP notification succeeded — remembering a failed injection would turn a retry into a silent drop). This closes both at-least-once holes: postToChannel's network retry and the scheduler's timeout+retry (the scheduler persists its delivery id on the job across attempts). The dedupe memory dies with the channel-server process ON PURPOSE — a StopFailure resend targets a fresh process and must land. Messages delivered since the last completed turn sit in the runtime's `pendingTurn` queue (capped at 10, oldest evicted first; replacing the single `lastUserMessage` slot, which could resend the wrong message and lose the right one) — cleared on `done` **and on every process death** (`dispose()`, covering `/stop`, Force Stop, `/new`, a plain disconnect, and a Cancel-turn kill), not just on `done`: a queue that survived a non-`done` death could resend a message whose work was explicitly stopped, which is exactly the bug a StopFailure landing after a Cancel-turn kill hit before this was fixed. The one path that still needs the queue's contents *after* a kill — the StopFailure auto-resend itself — reads them via a snapshot taken **before** calling `kill()` (see the StopFailure bullet above), not from the queue afterward. Net effect: a StopFailure after an intermediate `done` of a long task, or after any other process death, falls back to the generic "send your message again" notice instead of auto-resending — the deliberate, safe side of the trade-off; nothing is ever silently lost, only less automatic.
- **Stall alert**: The 5-minute response timeout notifies the user with a force-stop button when there's no reply *and* no active tool (the stuck-tool watchdog covers active tools). Re-arms itself if it fires while a tool is mid-flight, and stops the typing indicator when it alerts. The stuck-tool watchdog tracks an in-flight tool *count* (PreToolUse++ / PostToolUse--), so parallel tool calls can't disarm it early.
- **Cancel current turn is best-effort, not confirmed** (`src/cancel.ts` + `ProcessManager.interruptTurn`): `/stop` was the only way to interrupt Claude — a full kill of the PTY process. `/cancel` (and a "⏹ Cancel turn" button on long-running-task alerts) instead writes **Ctrl+C** (`\x03`) into the PTY — verified live that plain Escape (`\x1b`, Claude Code's *interactive*-mode `chat:cancel` binding) has zero effect on an actively-running Channels-mode turn; Claude Code's current keybinding reference separates `chat:cancel` (Escape) from the actual `app:interrupt` action, bound to Ctrl+C. This is deliberately best-effort, not a signal and never `kill()`: on Claude Code ≥2.1.246 (verified live + headless 2026-08-26) `Stop` fires once per turn and carries `last_assistant_message`, but a turn's *end* still doesn't confirm a mid-turn Ctrl+C did anything — the interrupt could have landed a token before completion, missed entirely, or hit a turn that was already wrapping up — and an async subagent means "the turn" can itself be several concurrent segments, so no hook event can be safely read as "the interrupt worked" — teleclaude never claims a confident "cancelled," only "⏳ Interrupt sent…". What IS guaranteed: `ProcessManager.hasCancelPending` is a sticky fence — set the instant Ctrl+C is first sent, for that process's entire remaining lifetime, cleared only by the process itself being torn down (never by a `done`/`error` hook) — and `message.ts`'s StopFailure handling reads it *before* calling `kill()`, so a pending cancellation can never be misread as an ordinary failure and trigger the pre-existing auto-resend-on-error recovery, which would otherwise redo the work the user just asked to stop. There's deliberately no follow-up "still running, force stop?" nudge after a grace period — a live test caught that firing on a cancel that had actually worked, since a successful Ctrl+C is *supposed* to leave the process running (that's the point of a soft interrupt over `/stop`), so "still running" isn't evidence either way. A genuinely stuck session is still caught by the existing stall/watchdog alerts on their own schedule, which offer "🛑 Force stop session" — a real, confirmable kill — the same way any other stuck session would. The "Cancel turn" and "🛑 Force stop session" *buttons* (not the `/cancel`/`/stop` commands, which always target whatever the topic is currently running — there's only one process per topic, so there's no "wrong turn" to protect against) both carry a short per-render token (`ProcessManager.beginTurn`'s seq+nonce, validated by `turnTokenMatches` in `cancel.ts`) so a stale alert whose retire-edit failed can't be tapped into interrupting — or force-killing — unrelated new work; a token-less Force Stop button (rendered when no turn had begun) stays valid only while the topic still has no begun turn.
- **Session names go through Claude Code's own naming, not a teleclaude label** (`src/session-name.ts`, `rename.ts`, `claude-session-registry.ts`): Claude Code names every session itself (`nameSource: "derived"`, e.g. `todo-c6`) and exposes two overrides — `-n/--name` at launch and the `/rename` slash command. `/new <name>` uses the flag; `/rename <name>` types `/rename <name>` into the PTY, the same channel `/cancel` uses for Ctrl+C, then presses Enter as a *separate* write 150ms later (`RENAME_SUBMIT_DELAY_MS`) — on 2.1.234 one write with a trailing `\r` worked, but on 2.1.308 a long enough single write is taken as a paste and the `\r` is dropped (verified live: a 64-char name never submitted in one write, renamed in ~400ms when split). Driving the real thing rather than storing a private label is what makes Claude *itself* aware of the name — a rename injects a system reminder ("The user named this session …") — and keeps the terminal `/resume` picker, prompt box and terminal title in agreement. **Unlike `/cancel`, this one is verifiable and so it does claim success**: Claude Code rewrites `~/.claude/sessions/<pid>.json` (keyed by the PTY child's pid, teleclaude spawns included) with the new name within ~500ms, so `requestRename` reads it back and reports the *actual* name — including the "another live session already holds that name" case, where Claude Code picks a variant and we report that instead of the request. Nothing is claimed when the read-back doesn't change. The name is persisted per topic in `sessions.json` and re-applied by every spawn, because it would otherwise die at the next `/model` switch, boot auto-spawn or resume. Names are sanitized before they reach the PTY (`sanitizeSessionName`) — control characters are stripped because a newline would submit the command early and turn the rest into an ordinary prompt for Claude — and escaped before they reach Telegram, since a name is user text going into a `parse_mode: "HTML"` message.
- **Pinned session-name message** (`src/session-pin.ts`): each topic keeps ONE pinned bot message ("📌 <name> · <model>") that is *edited in place*, never re-pinned — so the pinned bar always names the session the topic is talking to, and the "pinned a message" service noise happens at most once. The name is read from Claude Code's live-session registry via the PTY pid (`readLiveSessionName` — derived names included, so never-renamed sessions show up too), falling back to the persisted `SessionEntry.name`. Refreshed on the same once-per-turn `doneDebounce` as `/notify`/`/review`/`/receipts`, and immediately after `/rename`. Default ON per topic (`pinSession` **absent = enabled**, unlike the other toggles); `/pin` toggles it, and off unpins + deletes the message. The pin is recreated only when the tracked message was hand-deleted ("message to edit not found") — a *transient* edit failure deliberately never recreates, since that path double-pins on recovery. A pinChatMessage failure (bot lacks the "Pin messages" admin right) deletes the carrier message and warns once per topic per daemon lifetime. The bot's own "pinned a message" service message is deleted by a `message:pinned_message` handler registered BEFORE the auth middleware in daemon.ts — the service message's `from` is the bot itself, which the whitelist middleware would silently drop (scoped to the bot's own pins; a human's pin falls through untouched).
- **Spawn settings are one object, not a tail of positional arguments** (`SpawnSettings` + `spawnSettingsFor`): `spawn()` grew to `(chatId, topicId, path, sessionId, model, permissionMode, doneNotify, effort)` and `name` would have been a ninth — with `model`, `effort` and `name` all `string | undefined`, a swapped pair type-checks cleanly and only shows up as a session running the wrong model. All seven spawn call sites now build settings from persisted state through the single `spawnSettingsFor(saved, overrides)` helper, so a newly persisted setting can't be silently dropped by the one path nobody updated (`name` is exactly that kind of setting), and the defaults live in one place instead of six.
- **Per-topic scratch state lives in one TopicRuntime, not scattered maps** (`src/topic-runtime.ts`): message.ts/daemon.ts used to hold ~12 module-level topic-keyed maps (typing/stall/done timers, last reply, last user message, blocked-at, reply counts) with cleanup hand-maintained in 5+ places and several maps never cleaned at all. Each (chat, topic) now owns a `TopicRuntime` — a named-slot `TimerBag` (typing/typingStop/stall/softWarn/doneDebounce) plus scratch fields — fetched via `topicRuntime(chatId, topicId)`. One `dispose()` runs on the ProcessManager's `killed`/`disconnected` events and clears every timer plus the *process-scoped* fields — which now include the `pendingTurn` delivery-envelope queue (see "Delivery is idempotent and ledgered" above): a process death that isn't a completed turn must drop whatever was queued, or a later StopFailure could resend a message whose work was already stopped. Two fields deliberately SURVIVE dispose, and each survival is load-bearing: `topicReady` (owned by the spawn closure's own finally; the disconnected-notice suppression reads it after the process exited) and `channelBlockedAt` (gates respawn of a blocked topic AFTER its process is killed). The StopFailure auto-resend still works despite `pendingTurn` NOT surviving: the error branch snapshots `takeResendable()` before calling `kill()`, and `kill()`'s `killed` event (fired synchronously, before `kill()` returns) is what runs the dispose that empties the queue — so the snapshot is safely captured first. Full removal (`removeTopicRuntime`) happens only on `/delete`. The ProcessManager's own `processes` map stays where it is — it owns PTY mechanics; TopicRuntime is the scratch state around it.
- **Unnamed sessions get named after their first finished turn** (`src/auto-name.ts`, config `defaults.autoNameSessions`, default true): Claude Code writes an `ai-title` only for sessions it sees typed prompts in, so a channel-driven session stayed `<dir>-<2hex>` in `/sessions` and the terminal `/resume` picker forever. On the done-debounce (before the pin refresh, so the pin shows it the same turn) teleclaude sends one bare `/rename`, which makes Claude Code generate a name from the conversation (~1.6s, observed live) and record it in the transcript (`custom-title`). Gated on the live registry: `nameSource === "derived"` (anything else is a name somebody chose — and Claude Code restores a renamed session's name itself on `--resume`, `nameSource: "user"`), `status === "idle"` read right before typing (mid-turn the text would queue as a prompt, and with a permission dialog open the Enter would answer it), no persisted topic name, and one attempt per pid (`TopicRuntime.autoName`). The generated name is deliberately **not** written to `sessions.json`: a persisted name is re-applied with `-n` on every spawn, which would stamp it onto a different session the topic later resumes.
- **A name set with `-n` is invisible to the transcript** — `/rename` writes three records into the JSONL (`{"type":"custom-title"}`, `{"type":"agent-name"}`, and the older `<local-command-stdout>Session renamed to: …` line, all three from one rename on 2.1.234), but `-n` writes none. `sessions.ts` reads all three shapes (structured first, stdout kept for older transcripts) so `/sessions` shows renamed sessions by name, and `/sessions` additionally prefers the topic's persisted name for its *current* session id, which is the only place a `-n` name is recorded.
- **Resuming a session already open elsewhere is refused, not raced** (`src/live-sessions.ts`): Claude Code doesn't lock transcripts, so if a session id is live in a terminal (or any other Claude Code process) and Telegram resumes the same id, two processes end up appending to one JSONL file. `findLiveSession` scans Claude Code's live-session registry (`~/.claude/sessions/<pid>.json` — the same file `claude-session-registry.ts` already reads for `/rename` verification) for an entry whose `sessionId` matches and whose pid is still alive (`process.kill(pid, 0)`; EPERM counts as alive, ESRCH as dead). `resumeGuardDecision` allows the resume when there's no live match, the match is stale, or the live pid IS the topic's own current process (`ProcessManager.getPid`) — and refuses otherwise, naming the pid that holds it. Both `/resume <id>` and the `/sessions` resume buttons go through this: `resumeSession` (`src/handlers/resume.ts`) now returns `{ok:true} | {ok:false, reason:"not-found"|"live-elsewhere", ...}` instead of a bare boolean. v1 refuses outright — no "steal" (kill the other process) option; that's deferred. `/sessions` marks any listed session with 🔺 when `isSessionLiveElsewhere` finds it alive elsewhere too (checked for at most the ~10 listed ids per call — cheap, no cache needed).
- **`/handoff` hands a topic's live session to a terminal, deliberately one-way** (`src/handoff.ts` + the `handoff` command in `src/handlers/commands.ts`): resolves the topic's current session id (the running process's, via `pm.getSessionId`, else the persisted one), stops the process if one was running (the same graceful SIGINT `kill()` every other command uses — the next message in the topic still auto-resumes it, nothing is cleared), and replies with a copy-paste `cd <path> && claude --resume <id>` block plus an explicit two-writer warning: finish the terminal work before sending another message here, since Claude Code doesn't lock transcripts and both would append to the same one. The `cd` target prefers the persisted per-session `sessionCwd` (a worktree-homed session hands off at its worktree, not the root — see the worktree-sessions bullet above), falling back to the project root. This is the "Telegram → terminal" half of session handoff; the reverse direction is the existing `/sessions` + resume flow, now guarded by the live-session-registry check above so a terminal session already holding the id can't be silently raced.
- **Kill uses SIGINT, not the node-pty default** (`ProcessManager.kill`): every `/stop`, `/new`, `/model`, `/permissions`, `/effort` switch, and Force Stop tap funnels through the same `kill()`. Claude Code 2.1.132+ treats an externally delivered SIGINT as a graceful shutdown — flushing session/transcript state and printing a resume hint — rather than just dying. Since every one of those call sites already relies on the *next* message resuming via the persisted session id (`/stop` never clears it; only `/new` does), SIGINT makes that resume more reliable, not just faster.
- **Workspace trust can be pre-accepted, skipping half the startup-dialog dance** (`src/claude-trust.ts`): Claude Code's own "workspace not trusted" error names the fix directly — set `projects[<path>].hasTrustDialogAccepted: true` in Claude Code's global `~/.claude.json` (confirmed by inspecting the installed binary; not part of the public settings schema, so treat it as an implementation detail that could change). `preTrustWorkspace()` runs at every project-creation call site (the `mkdir:yes` flow, `/new`, and `/ls`'s picker) and does a narrow, best-effort read-modify-write of just that one field for that one project — never touching any other project's entry — since `~/.claude.json` is shared, hot, and actively written by every concurrently running Claude Code process on the machine, not just teleclaude's. A lost race with a concurrent write only reverts some *other* project's entry to what this read saw (recoverable — Claude Code rotates its own backups in `~/.claude/backups/`), never data loss. The dev-channels warning has no equivalent bypass — `awaitsPromptConfirmation`'s PTY-scan (below) still handles that one.
- **Long-running-task warnings are one shared, severity-monotonic alert** (`src/turn-warnings.ts`): the tool watchdog (2min soft / 5min hard, tool-level) and the turn-level stall timer (now soft at `stallAlertMinutes - 2min` / hard at `stallAlertMinutes`) used to render two independent, inconsistent messages. Both now render through `showTurnWarning`, which tracks one Telegram message per topic: a hard alert upgrades an existing soft message in place rather than sending a second one, and a soft warning is dropped outright once a hard alert is already showing. A failed edit of the tracked message (deleted, edit window expired) falls through to a fresh send in the same call — hard escalations are one-shot, so a swallowed edit would cost the only Cancel/Force-Stop alert. Every hard alert offers both remedies — "⏹ Cancel turn" and "🛑 Force stop session" — never just one. No periodic "N min elapsed" heartbeat ticking — deliberately cut per the design review to avoid a second recurring timer and stale-edit races; revisit only if a single warning proves insufficient in practice.
- **Readiness for delivery needs a green *port*, not just a hook** (`channel-ready.ts` + `waitForReady`): `channelStatus="registered"` comes from the first token-valid hook callback, which proves Claude Code is alive and channels aren't blocked — and nothing about the MCP channel server, an `npx tsx` subprocess that binds its port seconds later. `waitForReady` used to return `"ready"` the moment that status flipped, without ever probing the port: measured live, the hook lands at **4.6s** and the port answers at **8.0s** (≈1s vs ≈1s+ when resuming), so a `/new` followed straight away by a message POSTed into a socket nobody was listening on — `POST to :<port> failed fetch failed` — and the failure path then killed a perfectly healthy session. Reproduced in production twice (2026-08-13, 2026-08-18, identical signature: `server ready on :<port>` ~1s after spawn, immediate POST failure, `killed`). The HTTP probe is now mandatory and `registered` only buys skipping the post-`/ready` grace wait — which exists solely to catch a late block banner, and a hook is proof none is coming. The decision lives in one pure `readinessDecision()` with a regression test asserting a hook alone is never ready. Two supporting changes: the probe sends `x-teleclaude-token`, and a channel server answers **409** to a token that isn't its own, so a server still shutting down on a **recycled port** can't report readiness for the spawn that now owns it (the token is compared, never echoed — it's the server's own auth secret); and a network-level POST failure now re-verifies readiness and retries **once** (`postToChannel`) instead of killing the session on a timing artifact, still refusing to retry a topic that has since been killed or replaced. Both loopback fetches are bounded (`loopbackFetch` in message.ts: 5s readiness probe, 30s delivery POST — the channel server's own Telegram calls time out at 20s, so 30s can't fire on a healthy server): Grammy handles updates sequentially, so one wedged socket would otherwise stall every topic, and a timeout takes the same failure path as a refused connection.
- **Generation-aware spawn lifecycle**: `waitForReady` carries the spawn generation (spawnToken) and returns `"gone"` if the topic is killed/restarted mid-wait; all failure-path kills go through `killIfSameGeneration` so a timeout/block/POST failure can never kill a newer process. The "already running" path also waits for channel readiness before POSTing — direct spawns (boot, /model, /permissions, /resume) take seconds to bind their channel port. Startup timeouts retry the spawn once, then notify the user; all delivery failures notify instead of dropping silently.
- **Atomic state writes, private by default**: config/projects/sessions files are written via temp+rename (`fs-util.ts`) with mode 0600 (rename carries the temp mode, so pre-existing 0644 files tighten on their next write), and `~/.teleclaude` is created/tightened to 0700 — the dir holds the bot token and every id another local user shouldn't read. Corrupt files are preserved as `.corrupt-<ts>` and tolerated on load (no crash loop under launchd KeepAlive) — including `sessions.json`, which used to be the one state file silently reset to `{}`.
- **Tests never touch the real state dir** (`session-state.ts`): `loadSessionState(dir?)` fixes where sessions.json lives for the whole process (daemon boot passes its configDir; tests pass a mkdtemp dir), and `saveSessionState` throws under vitest if it would write the real `~/.teleclaude` — the suite runs on the live machine on every `npm version`, so a test that forgets to point session-state at a temp dir fails loudly instead of corrupting (and racing) a running daemon's store.
- **android/ios MCP tools**: the channel server exposes `android` (adb/emulator: launch, install APK, tap/swipe/type/key, shell, screenshot) and `ios` (xcrun simctl + idb: boot, install, launch, open URL, `idb ui` interactions, shell, screenshot) so Claude can drive local emulators/simulators; screenshots are sent to the topic. idb interactions use the `idb ui <cmd>` subcommand family.
- **Permission mode is `auto` by default, not bypass** (`permission-mode.ts`): teleclaude used to spawn *every* session with `--dangerously-skip-permissions` — no checks at all, on a bot anyone in an allowlisted group can drive from a phone — and that was the fallback for any topic with no persisted choice. Now the default is `--permission-mode auto`: a classifier vets each action and blocks the escalation/exfiltration/destruction classes while routine local work still runs unprompted. It fails soft in the direction we want — when the classifier blocks 3 in a row (or 20 in a session), or when the topic's model doesn't support auto mode, Claude Code falls back to *prompting*, and our permission relay turns those prompts into Telegram buttons. `/permissions` picks the mode per topic (buttons or argument) — it replaced `/bypass`, which was a two-state toggle that couldn't express three modes. Bypass is still reachable, just no longer one keystroke away. A legacy `bypass` boolean in `sessions.json` is still honoured (it was an explicit choice made with the old command) and cleared the next time the mode is set. Note the `--allowedTools` entries for our channel tools are narrow per-tool rules, which auto mode carries over — it only drops broad grants like `Bash(*)` or `Agent` rules. Mode is fixed at launch, so any change kills and respawns the topic. Read it via `effectivePermissionMode()`, never `pm.getPermissionMode()` directly: a stopped topic has no process and ProcessManager answers with the global default, so a stopped bypass topic would otherwise report itself as auto.
- **Sessions load only our MCP server** (`--strict-mcp-config`, config `defaults.strictMcpConfig`, default true): `--mcp-config` is *additive*, so without this every topic also inherited whatever MCP servers were configured globally — verified live, a plain spawn was opening an HTTP transport to `a third-party MCP server` on every topic (18 references in the debug log; 0 with the flag). That made a topic's tool surface depend on unrelated installs, added auth/elicitation prompts nobody can answer from a phone, and could introduce a new-MCP-server consent dialog that the spawn's two-prompt timed-Enter sequence doesn't expect. Set `strictMcpConfig: false` if you deliberately want a global MCP server reachable from Telegram.
- **MCP elicitation is declined, not left to hang** (`elicitation.ts`): a server asking the *user* for form input blocks the turn on a dialog rendered in a PTY nobody watches. Unlike a permission prompt there's no async verdict channel — the `Elicitation` hook's response *is* the answer and it's synchronous, so waiting for a Telegram tap would stall the turn for as long as the user takes. The daemon answers `action: "decline"`, tells the topic, and injects a system note telling Claude not to retry and to ask via the reply tool instead. `--strict-mcp-config` makes this rare by construction (our channel server never elicits), so this is the belt to that braces.
- **`AskUserQuestion` is relayed via our own blocking `ask_user` tool, not left to hang** (`ask-relay.ts` + `channel-server.ts`): the built-in picker is interactive-terminal-only and Claude Code has no sanctioned way to inject a structured answer back into it (verified in the binary — only permission prompts get a bidirectional verdict channel). `ask_user` is our own MCP tool, same shape (`questions[]`/`options[]`/`multiSelect`), whose handler `await`s `AskRelay.ask()` — a real Promise, not context-injection — while Telegram renders numbered buttons (multi-select adds ✅/⬜ toggle + Submit) plus "✏️ Write my own answer" and "❌ Cancel". A `PreToolUse` fallback in `daemon.ts` denies the real `AskUserQuestion` if Claude calls it anyway and redirects it to `ask_user` via `additionalContext` (server instructions ask it not to first) — deliberately skipping `trackToolUse`, since a denied call gets no `PostToolUse` to disarm the stuck-tool watchdog.
  - Button taps match `ASK_VERDICT_RE` (`ask:<verb>:<id>[:<idx>]`) *before* the inbound handler treats them as chat, so they can never start a fresh turn. Freeform answers use Telegram's native `force_reply`, not "whatever the next message says": `matchCustomReply` only fires for an explicit reply to that exact prompt (threaded via `sendToChannel`'s `meta.reply_to_message_id`), and separates "never a custom prompt" (falls through as chat) from `"closed"` (resolved another way — swallowed with a notice).
  - **Exactly-one resolution path, enforced.** `claimCustom()` makes entering custom-answer mode synchronous and exactly-once; `pick`/`toggle`/`submit`/`cancel` all then refuse for that request, so nothing can race the custom flow to close it out from under an in-flight or just-sent ForceReply prompt. A claim that never produced a usable prompt (both sends failed) is released via `releaseCustomClaim` so a retry isn't locked out.
  - **Two Telegram messages, two owners.** The original question message is retired exactly once, by the tool handler's own `await ask(...)` continuation (it has the "question i of n" context the relay's timeout callback doesn't — a second edit there would race it). The ForceReply prompt is a *separate* message the tool handler can never reach; `onTimeout` and the custom-answer-received path retire it directly, since they're the ones actually closing that request. It's sent via `sendPlainOnce` (single attempt, no HTML, no retry) rather than the question's `sendAskPrompt` — its message id is load-bearing for `matchCustomReply`, so a retry-after-ambiguous-failure risks silently orphaning whichever copy didn't get registered.
  - **HTTP response flags, not just "ok".** `{consumed:true}` tells `sendToChannel` (`message.ts`) this POST was a relay verdict, not a chat turn, so it restores whatever was resendable beforehand instead of letting a later StopFailure resend a bare answer like "use tRPC" with no question attached. `{handled}` separately reports whether a *live* relay entry actually matched — a stale tap against a respawned topic's fresh, empty relay still gets a 2xx, so `handled` is what lets `handlers/index.ts` show an honest "may have already closed" toast instead of a false "✅ Got it".
  - **MCP tool names in hook payloads are fully qualified** (`mcp__teleclaude-channel__ask_user` — "teleclaude-channel" is our `--mcp-config` server key), not the bare name registered in `channel-server.ts`. Bit us twice: the watchdog exemption below must match the qualified form, and `ask_user` was missing from `--allowedTools` entirely (added alongside reply/send_file/screenshot/browse) — without it, calling this tool hit the classifier like an untrusted one.
  - **The watchdog exemption cuts both ways.** `ask_user` is designed to block ~5 minutes waiting on a human, so `processes.ts` exempts it from the generic stuck-tool watchdog (2min warn / 5min force-stop) — but that also removes the only safety net for a hang *inside* it unrelated to waiting on a person, and `telegramPost` had no timeout at all. It now carries a 20s `AbortSignal`, closing that hole for every Telegram call in the file, not just this tool's.
  - **Accepted limitation**: this state lives entirely in the per-topic channel-server process's memory (same tradeoff `permission-relay.ts` already makes) — `/new`/`/stop` kills any pending question for free, but a restart also drops the "closed" memory, so a stale button/ForceReply reply against a since-dead process just falls through as ordinary chat instead of a "this already closed" notice.
- **Auto-mode denials are forwarded to the topic** (`permission-denied.ts`): when the classifier blocks an action, Claude Code tells *Claude* ("Blocked by classifier") and shows the user a TUI notification plus a `/permissions` → Recently denied entry — none of which exists on a phone, so from Telegram the block is invisible and Claude just silently pivots. The `PermissionDenied` hook is forwarded to the topic with the tool and an input preview. Observability only: the denial already happened, and the hook's `{retry:true}` would just be blocked again unchanged, so escalation is left to Claude Code's own fallback (3 consecutive blocks → it starts prompting → our relay turns that into Telegram buttons). Notices are throttled per `(topic, tool, input)` for 60s, because a blocked action gets retried in bursts; distinct blocks still all get through. Sent as plain text with no `parse_mode` — the preview is a raw shell command and nothing in it should be able to break the send.
- **Dead hooks in project settings are swept at boot** (`sweepProjectHooks`) — a migration now that hooks are per-spawn, but it earns its keep: the old per-project hooks were only pruned for the project being spawned, so a project driven from a *terminal* kept its fossils forever. Found live: an old `UserPromptSubmit` → `event=working` hook still POSTing on every prompt, with no chat id and no token (so it skipped the auth guard and landed in the daemon's "unhandled" branch), months after that event was removed — 177 dead hooks across 21 of 22 project settings files. The daemon now prunes every teleclaude hook URL from every known project's `settings.local.json` at startup, *before* auto-spawn: at that moment no spawn is alive, so every such hook is dead by definition and spawning re-adds a live one. Unparseable settings files are skipped rather than truncated, and files with nothing to prune aren't rewritten.
- **`reply`/`send_file` are pinned into context**: Claude Code defers MCP tool schemas behind `ToolSearch` by default, and `reply` is needed on *every* turn — logs showed two `ToolSearch` calls (~9s) before each reply. Both tools carry `_meta: { "anthropic/alwaysLoad": true }` (Claude Code ≥2.1.121). Deliberately per-tool, not the server-wide `alwaysLoad` config flag, so the large `android`/`ios`/`browse` schemas stay deferred and out of context.
- **The reply-tool reminder fires once per spawn, not on every message** (`src/channel-server.ts`): the "IMPORTANT: you must use the reply tool" prefix used to be prepended to every injected message — needless noise once Claude has already internalized it for the session. A module-level `firstInjectionDone` flag (flipped *before* the `await`, so a concurrent retry can't double-prepend) now prepends it only to the first message a channel-server process ever injects; every later message that process handles passes through verbatim. The flag lives and dies with the process, so a fresh spawn (`/new`, `/model`/`/effort`/`/permissions` switch, a respawn after a crash) always reminds once. Accepted gap: if that very first injection fails, the flag is already flipped and the retry lands reminder-less — covered by three independent nets: the MCP server's own instructions (which state the same requirement), `channel-instructions.ts`'s post-compaction system-reminder re-injection, and the `/forward` fallback that still delivers the turn's `last_assistant_message` even when Claude never calls the reply tool at all.
- **`send_file` is contained to the project directory** (`path-containment.ts`): the tool is pre-approved via `--allowedTools`, so in auto mode the permission classifier never vets it — it used to read *any* absolute path, letting a prompt-injected repo exfiltrate `~/.ssh` keys or the MCP config (bot token included) to the Telegram topic. `resolveWithinRoot` realpath-resolves both the requested file and the project root (`TELECLAUDE_PROJECT_PATH`, passed in the MCP env), rejects anything outside the root — including symlinks inside the root pointing outside — and caps files at 50MB (Telegram's own document limit). No root configured means fail closed. Screenshot paths (`sendPhoto`) are exempt by design: they're generated internally in `/tmp` by our own code, never caller-supplied.
- **`send_page` renders markdown into a styled offline HTML document** (`page-render.ts` + `channel-server.ts`): the generalization of /diff's delivery shape — Claude passes title + markdown, the server wraps it in a dark-mode-aware template in the same spirit as /diff's (separate code — page-render.ts owns its own CSS) and uploads it from memory via `sendDocument` (no temp file, never touches the project repo, so `send_file`'s path containment is irrelevant: the content is Claude-authored, adding no exfiltration surface beyond `reply`). GFM tables/fenced code supported via `marked`; inline HTML passes through as the escape hatch. Content capped at 2MB (in-app-browser comfort, same rationale as `DIFF_HTML_MAX_PATCH_BYTES`). The schema stays deferred (NOT `alwaysLoad` — it's not per-turn like `reply`); discoverability comes from the server instructions line and `channel-instructions.ts`'s post-compaction reminder. The template must stay offline-only — a test asserts no `http(s)://` comes from it.
- **Screenshots can come back to Claude, not just the user**: `screenshot`/`browse`/`android`/`ios` accept `return_image: true`, which appends the *final* screenshot to the tool result as an MCP `image` block so Claude can see what it captured (tap → look → tap on an emulator). Opt-in, because Claude Code counts image payloads against `MAX_MCP_OUTPUT_TOKENS` and the `anthropic/maxResultSizeChars` annotation does not apply to images. `image-content.ts` downscales through `sips`/`magick`/`convert` on a ladder (900px/q60 → 700px/q50, measured: a text-dense 1280x800 page is 75KB and legible at the first rung) and refuses to inline anything over 90KB encoded; `processes.ts` raises `MAX_MCP_OUTPUT_TOKENS` to 45000 for the spawned session unless the user set it. When the image can't be inlined the tool result *says so*, so Claude doesn't act as if it saw it.
- **Headless Chrome runs with `--disable-gpu` and a 60s protocol timeout** (`launchBrowser` in `src/screenshot.ts`, shared by `screenshot`/`browse`/the `/diff` image preview): new-headless Chrome on macOS never completes `Page.captureScreenshot` while the Mac's display is asleep — navigation succeeds, the capture hangs, and puppeteer's default 180s `protocolTimeout` is what finally fails it. Found live 2026-10-22: two screenshots of a live site failed identically during a 16-hour display-off window, the same page captured in ~1s minutes after the display woke, and a controlled `pmset displaysleepnow` run reproduced it (41s to timeout with the GPU process, ~1s with `--disable-gpu` or `headless: "shell"`, same binary, same page). The GPU process waits on a display that isn't drawing; software rendering doesn't. `--disable-gpu` was chosen over shell mode because it keeps the same binary and rendering path. The 60s `protocolTimeout` bounds any future stall so the tool fails before Claude Code's 120s background-task threshold and our stuck-tool watchdog, instead of 3 minutes later. A daemon driven from a phone runs most captures with the display asleep, so this isn't an edge case.
- **Diff rendering stays offline and browser-free in tests** (`src/diff-render.ts` + `src/render-images.ts`): the `/diff` HTML document (diff2html, CSS inlined via a memoized `createRequire(...).resolve()` read) must render with zero network access — Telegram's in-app browser has none — so nothing in it may reference an external URL; a test asserts no bare `http(s)://` appears anywhere in the generated document. `DIFF_HTML_MAX_PATCH_BYTES` (4MB) skips the HTML attachment (not the `.patch`, which has its own much larger cap) for a diff too big for an in-app browser to handle comfortably. The paged-PNG preview (`renderHtmlToImages`, puppeteer via the `launchBrowser()` shared with `/screenshot`) is **never called from a test** — no test in this repo may launch a browser, since `npm test` runs on the live dev machine on every `npm version` — so its pure page-slicing math (`pageClips`) carries all the automated coverage and the renderer itself is verified live. Its `DEFAULT_MAX_PAGES` (10) tracks Telegram's own `sendMediaGroup` cap, not an arbitrary round number.
- **Everything relayed into a Telegram HTML message must be escaped**: the permission relay interpolates `tool_name`/`description`/`input_preview` (model-authored, documented as untrusted) into `parse_mode: "HTML"`. A bare `<` or `&` makes Telegram reject the send, so the 🔐 prompt never arrives and the turn hangs until the 5-minute auto-deny. All three go through `escapeHtml`, and are clipped to a budget (the client relays up to 3,500 code points *per field*, which overflows Telegram's 4096 on its own). The auto-deny is armed **before** the send, and a failed HTML send retries as plain text — previously a rejected send left no timer at all, so the dialog waited forever.
- **A permission prompt answered at the terminal is never reported back to us** (`permission-relay.ts`): the relay is parallel by design — terminal dialog and Telegram prompt both live, first answer wins — so a pending entry here can already be dead, and the timeout used to inject "auto-denied" as fact about a call that had actually run. Two signals now mark an entry answered, and **neither cancels the auto-deny**: `PostToolUse` for that tool name (suggestive only — parallel tool calls mean an auto-approved `Bash` can finish while a *different* `Bash` awaits approval), and turn end via `/done` (near-certain, and additionally retires the dead buttons in the chat, once — `/done` fires per turn). Marking only suppresses the misleading notice. That asymmetry is the whole design: a wrong inference must cost a suppressed notice, never a stranded turn with no safety net. A verdict for an already-closed prompt is swallowed rather than forwarded to Claude as chat text ("yes abcde" as a chat message is worse than a dropped verdict).
- **Channel-block detection**: Channels require the org `channelsEnabled` setting (claude.ai/admin-settings/claude-code). When off, Claude Code binds the MCP port (so `/ready` looks healthy) but *silently drops* inbound messages. The PTY scanner (`channel-detect.ts` → `processes.ts`) parses the block banner over a rolling buffer, whitespace-insensitively (TUI rendering eats spaces), during the first 90s after spawn only, and marks the process `channelStatus="blocked"`. `waitForReady` returns `"ready"|"blocked"|"timeout"|"gone"` — a green `/ready` is not trusted alone; it waits a short grace for a late block banner. **"Registered" comes from hooks, not the PTY**: current Claude Code never prints the `inject directly` confirmation, so the first token-valid callback marks the channel registered (`pm.markChannelRegistered`, upgrade-only from pending). On blocked: per-topic alert, 2-min respawn gate, ONE global owner DM (deduped 30 min), and the blocked process is killed so the post-cooldown respawn can detect re-enabled channels.
- **Telegram command menu**: `bot-commands.ts` pushes `setMyCommands` for the `all_private_chats` / `all_group_chats` / default scopes, plus a per-chat scope for every owner DM and every group — Telegram picks the *most specific* scope that has a list, so per-chat lists must be complete. Scopes have no notion of a topic — there is no `BotCommandScope` for one, and the `/` autocomplete a client shows inside a topic is just the chat's list — so a forum group gets General + project commands merged into one menu. Seven names exist in both lists and mean different things per topic; a plain merge kept whichever description came first, so `/new` read "Create a project: /new <name> <path>" even in a project topic where it starts a fresh session. `GROUP_MERGED_DESCRIPTIONS` gives those a dual description ("Topic: … · General: …") and a test asserts the map covers exactly the overlap, so a future command added to both lists can't silently inherit the wrong half. Each chat's list also carries `/<project>` routing shortcuts; project names are normalized to Telegram's `[a-z0-9_]` rule by `normalizeRouteName` (lowercase, strip diacritics, `-`→`_`), and `resolveRoute` normalizes the same way so `/game_template` and `/cafe` route to `Game-Template` and `Café`. Names that would shadow a real command are skipped, and project creation refuses a name that folds to the same command as an existing one (`findRouteCollision`) — routing couldn't tell them apart. The menu re-syncs (debounced 2s) via the `onProjectsChanged` hook in `config.ts` `saveProjects`, so any future project mutation refreshes it without touching call sites.
- **Continue-at-reset picker**: the 🔴 quota-exhausted DM carries inline buttons (`continue-picker.ts` + `handlers/continue.ts`) — one toggle row per project that was working (running process, or a session active in the last 6h; ticked by default if running or active in the last 30 min, max 8 rows, most relevant first), plus "⏰ Continue at reset". Confirming writes one one-shot schedule per ticked project with the message "Continue working", timed for `resets_at + 1 min`, so the work picks up in the existing session. Guards: a picker whose limit reset more than 30 min ago refuses (it would otherwise schedule work for "now + 1 min" out of nowhere), and jobs are deduped per `(chat, topic, ~same runAt)` so two owners confirming the same alert can't queue the prompt twice. Selection state is in memory per message (a restart makes the buttons answer "expired"; anything already scheduled is in `schedules.json`), and the picker is consumed on confirm. A failure building the picker never costs you the alert itself — it falls back to plain text.
- **Scheduled runs**: `/at` / `/every` persist a job to `schedules.json`; a 30s tick in `scheduler.ts` mirrors `⏰ <message>` into the topic and hands it to the *same* `sendToChannel` path a human message takes — so spawn/resume, readiness waiting, blocked-channel handling and stall alerts all apply. Times are **host local**. **Delivery is verified, not assumed**: `sendToChannel` returns a `DeliveryResult` (it reports spawn failures, a blocked channel and POST errors instead of throwing), and the schedule is only advanced/deleted once a run actually reached Claude. A failed attempt retries in 5 min, up to 3 attempts, then gives up with a notice; the attempt counter is persisted *before* delivery so a crash mid-run can't loop. `lastRunAt` is only stamped for runs that happened. A run missed while the daemon was down still fires within a 30-min grace window; older ones are skipped with a note. Every await in a tick is bounded (4 min per delivery, 30s per Telegram call) and a tick running >15 min releases the overlap guard, so the scheduler can't be wedged by a hung socket. A quota gate (`budget-gate.ts`, config `defaults.schedulePauseAtPercent`) can defer due jobs while a bucket is above a threshold — checked before the attempt counter is spent, failing open on an unreachable quota API, with a ⏸ notice throttled to once per topic per hour. Limits: 50 jobs per chat, `/schedules` budgeted to fit one Telegram message, ambiguous `/unschedule` prefixes rejected. `--new` clears only the sessionId (like `/new`), `--model`/`--effort` persist for the topic; any of them kills a running process so the next spawn picks them up. Scheduling from a DM can target any project (like `/<project> <message>`); inside a group it stays within that group.
- **Done notification**: `/notify` toggles sending a non-silent "💬 Waiting for new message…" message on turn completion (default off). Triggers push notification.
- **Tool activity tracking**: Every tool use is logged with name, command, and start time. 2-minute watchdog warns user if a tool appears stuck.
- **Typing indicator tracks real work, stops on the confirmed final send**: Starts the moment a message is *accepted* (`beginTurnTyping` at the top of `sendToChannel`, before the spawn/readiness wait — a cold topic spends 8-30s there and used to show nothing; every delivery-failure exit stops it, directly or via the kill→dispose that clears all timers). Stays on through all activity (reply/tool_use/compaction). It stops only once the final update is *confirmed sent*, not on a blind timer: `event=reply` is posted by the channel server only after the Telegram send/edit completes (`deliverReply` awaits it), and the reply tool awaits delivery so `done` always lands after the final reply. So on `done` with replies>0 it stops after a short 2.5s settle margin; with replies===0 a `/forward` fallback send follows, and the daemon emits a `forwarded` event after that send so typing stops precisely (8s fallback if nothing is sent). Any later activity resets the pending stop, so multi-turn tasks never cut it off. Terminal events (error/killed/disconnected) stop it at once. `tool_use` is forwarded from the daemon to the event handler so long tool phases keep it alive. Two keep-alive subtleties (`keepAliveActionFor` in `typing-state.ts`): Telegram clients *clear* the typing status whenever a bot message arrives, so activity on an already-running indicator re-sends `sendChatAction` immediately instead of waiting up to 4s for the next interval tick — throttled to 1.5s, except a `reply` event, which is a *confirmed* bot send (the status was definitely just cleared) and bypasses the throttle; and an *unbacked* indicator run — one no in-flight delivery guarantees a `done` for: resurrected by activity from a full stop, **or** continuing past the point where done/forwarded scheduled its settle stop (the trailing-subagent case — `rt.typingUnbacked` is set the moment a stop is scheduled, so activity inside the 2.5-8s settle window inherits the cap rather than stripping the pending stop and running forever) — carries a 5-min idle cap that each further activity event pushes forward. A real delivery (`beginTurnTyping`) clears unbacked mode and its cap. Known accepted gaps: `stopTyping` on a failure path isn't generation-aware (a concurrent delivery's failure can briefly stop a newer delivery's indicator — bounded by the POST-ok re-assert), and the `tool_use` nudge fires before the activity render it anticipates (only the first render per phase is a new message; edits don't clear the status).
- **Symlink resolution**: Claude Code resolves symlinks for session storage. Use `realpathSync` for session lookup.
- **Port recycling — but never SIGKILL a stranger** (`port-guard.ts`): ProcessManager reuses ports from killed processes. The old `killPort` SIGKILLed *every* listener on the port before each spawn — on a user's machine that's their unrelated dev server on 8801. `sweepPort` identifies listeners by command line (`ps -o command=` contains `channel-server.ts` — the channel server is spawned by Claude Code, so teleclaude never holds its pid and command-line identity is the only option): recognized orphans are killed, a foreign listener makes spawn skip to a brand-new port (bounded, never re-offering the occupied one), and teardown sweeps the same way.
- **MCP config security**: Temp files written with 0o600 permissions, cleaned up on kill.
- **Hooks are per-spawn, not per-project** (`teleclaudeHookSettings` → `--settings <temp file>`): they used to be merged into the project's own `.claude/settings.local.json`, which meant they applied to *every* Claude Code session in that directory — the user's terminal sessions fired teleclaude's callbacks on every tool use, and the daemon had to recognise and reject them as foreign. It also wrote the spawn token into a file inside a repo, and left any retired hook key behind to fire forever. The hooks now live in `/tmp/teleclaude-mcp/settings-<chat>-<topic>.json` (0600 in a 0700 dir), deleted on kill with the MCP config. `--settings` *merges* with the file-based sources rather than replacing them — verified: a project-scope hook and a `--settings` hook for the same event both fire — so the user's own hooks still run. Verified before shipping that our generated file actually delivers `tool_use`/`tool_use_post`/`done`; if it ever stopped, done-detection would go with it.
- **Channel server HTTP auth — fail closed** (`http-auth.ts`): All inbound POSTs require the `x-teleclaude-token` header (per-spawn token, passed via env). Blocks other local processes from injecting messages/permission verdicts. The guard used to be `AUTH_TOKEN && header !== AUTH_TOKEN` — an empty env token accepted every POST. Now an empty token rejects all POSTs (401) and makes `/ready` answer 503, matching the daemon's own fail-closed callback guard; a mismatched token on `/ready` still gets 409 (recycled-port protection, token compared never echoed).
- **Activity edit coalescing**: Tool/task activity renders are batched behind a 1s timer to avoid Telegram edit rate limits. Replies render immediately.
- **/forward endpoint**: When Claude finishes a turn without calling the reply tool, the daemon forwards the last message straight to Telegram via the channel server's `/forward` — no extra Claude turn. If `/forward` itself fails (non-2xx, network error, 30s timeout), the daemon falls back to sending the raw text directly in plain chunks (`forward-fallback.ts`): a wedged channel server costs formatting at worst, never the finished answer.
- **Live turn view**: `TurnView` (`src/turn-view.ts`) supersedes `ReplyState` as the channel server's render state — same phase/task contract, plus incremental narration (assistant "thinking out loud" text) and per-tool outcomes (✓/❌ suffixes matched back to their `toolStarted` line by scope+fingerprint). Two new hooks feed it: `MessageDisplay` → `narration` (streamed chunks keyed by message/prompt id) and `PostToolUseFailure` → `tool_failed` (fires *instead of* `PostToolUse` on a failing call). The daemon forwards both, plus `/subagent` (agent start/stop/label rows, nested tool lines) and an extended `/tool-post` carrying the outcome (`deriveOutcome`/`snippet` in `src/tool-outcome.ts`, shared by the success and failure branches). Detail level is per-topic — `/live full | summary | off` (default `summary`) — persisted as `SessionEntry.liveView`, passed at spawn via `TELECLAUDE_LIVE_VIEW` and flippable at runtime via a `POST /live-mode` (`handlers/commands.ts`'s `switchLiveView`) with **no respawn**. `summary` mode collapses the live message to just its reply text (`renderFinal("summary")`) once the turn settles, and that collapse is **latched**: once collapsed, further live-activity renders for that turn are dropped so nothing can re-expand a message the user has already seen finalized. **`full`/`summary` also collapse each CLOSED phase while the message is still live**: a phase whose reply was already delivered renders as one `▸ N tools · M agents · Ns` line above that reply, instead of its full tool-line header — the still-running phase is unaffected and always keeps full detail (tool lines, narration, agent rows). `off` keeps the classic uncollapsed per-phase rendering, matching its "old behavior" contract. Driven by a public `TurnView.phaseCollapse` flag (default `true`), set from `liveMode !== "off"` both at spawn and on every `/live-mode` switch; per-phase tool/agent counters and an optional close timestamp (`closePhase(text, now?)`) feed the line, and a phase produced by `restore()` (the ask-relay rollback path) always renders as opaque full text with no ▸ line, since its counters are unrecoverable from the flat wire shape. **Delivery and the live view render differently on purpose**: actual reply delivery (`reply-delivery.ts`) uses `renderFull()` — uncapped — while the live activity view uses the budgeted `render()` (`MAX_RENDER_CHARS`, trims narration → nested tool lines → main tool lines → phases in that order); conflating the two broke long replies in review (a capped delivery render silently truncated an in-progress answer), so the split is load-bearing, not a style choice. The `PostToolUseFailure` branch also closed a watchdog leak: a failing tool used to never fire `PostToolUse`, so `toolCompleted()` never ran and the stuck-tool watchdog's in-flight count only ever went up.

## Commands

**General topic:**
- `/new <name> <path>` — Create project with forum topic (expands `~`)
- `/list` — List projects (🟢 = running)
- `/delete <name>` — Delete project + forum topic
- `/status` — Uptime, memory, running sessions
- `/usage` — Weekly token usage across all projects
- `/update` — Pull latest + restart (safe from chat: pre-flight checks in the live daemon, pull/install on confirm button, detached `launchctl kickstart`/`systemctl restart` survives the daemon it kills, and a marker file (`restart-notify.json`, 15-min TTL) makes the fresh daemon confirm "Back online" into the chat — `self-update.ts`). A bundled build without a `.git` checkout refuses to update — there's nothing to pull.
- `/restart` — Restart the service (same detached mechanism, confirm button)
- `/ls [path]` — Browse filesystem to create projects interactively
- `/at <when> <project> <message>` — Schedule a one-off run (`07:00`, `tomorrow 07:00`, `2026-08-02 07:00`, `+30m`)
- `/every <spec> <project> <message>` — Recurring run (`day 07:00`, `mon-fri 09:30`, `30m`, `"0 7 * * 1-5"`)
- `/schedules` — List schedules with ❌ cancel buttons; `/unschedule <id>`
- `/help` — Show commands
- `/<project> <message>` — Route a message to that project's topic session (also works as a DM to the bot). Acks `✅ → Name`, mirrors `📨 <message>` into the topic; Claude's reply appears there.

**Project topic:**
- `/new [name]` — Fresh Claude Code session (keeps chatId/model/effort/permissionMode — only the sessionId is dropped). With a name, the session launches as `claude -n <name>`; a bare `/new` *clears* any previous name
- `/stop` — Kill Claude Code for this topic
- `/rename [name]` — Name the running session (Claude Code's own `/rename`, typed into the PTY); no argument asks Claude Code to name it from the conversation
- `/cancel` — Cancel just the current turn (ESC into the PTY), keeping the session alive
- `/model` — Switch model via inline buttons (persisted); `/model <id|alias>` also accepted
- `/effort` — Switch effort level via inline buttons (persisted); `/effort <level|auto>` also accepted
- `/permissions` — Pick ⚡ Auto / 🔐 Supervised / ☠️ Bypass via inline buttons (persisted); `/permissions <mode>` also accepted
- `/status` — Session status, model, permissions
- `/usage` — Token usage, context window %, session totals
- `/screenshot <url>` — Screenshot a URL
- `/diff` — Uncommitted git changes: diff-stat summary in the topic, full patch attached as a `.patch` document (handles non-repo, clean tree, and oversized patches), plus a self-contained syntax-highlighted `.html` document (diff2html, inlined CSS, dark-mode aware, offline-only — skipped above `DIFF_HTML_MAX_PATCH_BYTES`/4MB) that opens directly in Telegram's in-app browser. When the HTML was produced, the summary message also carries a "🖼 Preview as images" button (`src/diff-image-callback.ts` + `sendDiffImagePreview` in `handlers/commands.ts`): re-collects the diff fresh, renders it via puppeteer (`src/render-images.ts`, `launchBrowser()` shared with `/screenshot`) to up to `DEFAULT_MAX_PAGES` (10) PNGs at `DEFAULT_WIDTH`x`DEFAULT_PAGE_HEIGHT` (900x2200), and sends them as one `sendMediaGroup` album — guarded per-topic (`topicKey()`) so a second tap while rendering answers instead of racing a duplicate render, with temp files cleaned up in a `finally`. The `/review` prompt's "Show diff" button reuses `sendDiffReport` (and therefore this button) for free.
- `/sessions` — List sessions with inline resume buttons; 🔺 marks one already open in another Claude process
- `/resume <id>` — Resume a specific session
- `/handoff` — Hand this topic's session to your terminal: stops it here (if running) and replies with `cd <path> && claude --resume <id>`
- `/notify` — Toggle push notification on turn completion (persisted)
- `/review` — Toggle a turn-end prompt (📄 show diff · 🤖 ask Claude to commit · ✔️ leave it) when a turn ends with uncommitted changes; rides the same once-per-turn done-debounce as `/notify` and dedups on the dirty-state signature so an unchanged tree isn't re-nagged (persisted, default off)
- `/receipts` — Toggle a one-line turn receipt (persisted, default off): `🧾 ⏱ <duration> · 🔧 <N> tools · ~<tokens> tokens out`. Rides the same once-per-turn `doneDebounce` as `/notify`/`/review` — no per-Stop hook, no new timer. Duration is time since the topic's last user message; tool count is `tool_use` events since the last delivered message (`TopicRuntime.toolCount`, reset on each successful delivery, not on `done`); tokens is a delta of the session's cumulative output tokens between receipts (`getSessionUsage`, baseline kept in `TopicRuntime.receiptTokenBaseline`) — the segment is silently omitted (never crashes) when there's no session/project, the transcript is missing or over 32MB, or there's no baseline yet (first receipt after a boot/respawn)
- `/pin` — Toggle the pinned session-name message (persisted, **default on**): one pinned bot message per topic showing the current session's name (live registry name, falling back to the persisted one) and model, edited in place after each turn and on `/rename`; off unpins and deletes it
- `/live [full|summary|off]` — Live turn view detail: full / summary / off via inline buttons; persisted; default summary
- `/at <when> <message>` / `/every <spec> <message>` — Schedule into this topic (project implied)
- `/digest [HH:MM]` — Preset recurring briefings (morning 07:00 / end-of-day 18:00 / weekly Mon 08:00) via inline buttons; persists as a normal cron job in `schedules.json` (all delivery/retry machinery applies), deduped per topic, cancellable via `/schedules`
- `/schedules` — This topic's schedules
- `/webhook [new|off]` — Provision an inbound webhook for this topic: `new` creates/rotates a per-topic token (shown once, never logged), `off` disables it. A POST of `{"message": "..."}` with the `X-Teleclaude-Token` header routes into the topic via the same `sendToChannel` path a scheduled run uses. Mounted on the daemon's existing **127.0.0.1** callback server (`src/webhook.ts` → `daemon.ts`); its own constant-time (`timingSafeEqual` over SHA-256), fail-closed token auth is separate from the hook-callback `x-teleclaude-token` guard. Message content is control-char-sanitized and capped (64KB body / 4000 chars); the token binds to its own `(chat, topic)` (no cross-topic routing). Local-only by design — expose via your own tunnel if needed.

## Config Files

- `~/.teleclaude/config.json` — ownerTelegramId (legacy), ownerTelegramIds (whitelist), showUsageStats, defaults.strictMcpConfig (default true), defaults.stallAlertMinutes, defaults.quotaAlertPercent (owner DM when a quota bucket crosses N%, once per reset window, 0=off; checked every 10 min — `quota-watch.ts`), defaults.autoNameSessions (name an unnamed session from the conversation after its first finished turn, default true — `auto-name.ts`), defaults.schedulePauseAtPercent (defer scheduled runs — never interactive messages — while the 5h quota bucket is ≥ N%; 0/unset = off; deferrals push a due job 15 min at a time without spending delivery attempts, and resume automatically below the threshold — `budget-gate.ts`). At 100% it sends ONE red "exhausted" DM and schedules a 🟢 "reset" DM for the bucket's `resets_at` instead of repeating. The reset check never claims "available again" on an unreachable quota API — it re-arms and looks again (5 attempts), and says so if it still can't confirm. Dedupe key = (bucket, level, reset window floored to the minute) — the API restamps `resets_at` with per-request microseconds, so the raw string is not stable.
- `~/.teleclaude/projects.json` — project list (name, path, chatId, topicId)
- `~/.teleclaude/bot_token` — Telegram bot token
- `~/.teleclaude/sessions.json` — active sessionId/chatId/permissionMode/model/effort/name/lastActiveAt/pin state per topic, keyed `chatId:topicId` (legacy `bypass` boolean still read)
- `~/.teleclaude/schedules.json` — scheduled jobs (`/at`, `/every`): target `(chatId, topicId)`, message, kind (once/cron/interval), `nextRunAt`, flags
- `/tmp/teleclaude-mcp/topic-*.json` — MCP server configs (temp, cleaned on kill)
- `/tmp/teleclaude-mcp/settings-*.json` — per-spawn hook settings passed via `--settings` (temp, 0600, cleaned on kill). teleclaude no longer writes into any project's `.claude/settings.local.json`; `sweepProjectHooks` removes what older versions left there.
